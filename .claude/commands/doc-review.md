# Documentation Content Review

Review changed documentation files against the ExpertFlow CX content guidelines.

**Scope:** "$ARGUMENTS" (blank = current working diff against main)

---

## Step 1 — Load the authoritative rules

Read both rule files in full before evaluating anything:

1. Read `Phase3/Content_Placement_Guide.yaml` — placement rules, frontmatter spec, section definitions, edge cases, audit triggers
2. Read `Phase3/Persona_Model.md` — persona definitions, audience tag values, golden paths

---

## Step 2 — Identify changed files

```bash
# If no argument provided:
git diff main --name-only -- 'docs-site/docs/cx/**/*.md' 'docs-site/sidebars.js'

# If a branch or commit was provided as argument, use:
git diff main...$ARGUMENTS --name-only -- 'docs-site/docs/cx/**/*.md' 'docs-site/sidebars.js'
```

List the changed files. For each `.md` file, also read its full content.

---

## Step 3 — Review each changed markdown file

For every changed `.md` file, run through the following checklist. Report each item as PASS, FAIL, or WARN.

### 3a. Frontmatter completeness

Check all required fields are present and valid:

| Field | Rule |
|---|---|
| `title` | Present, non-empty string |
| `summary` | Present, one sentence describing what the doc covers |
| `doc-type` | One of: `how-to`, `tutorial`, `explanation`, `reference`, `landing` |
| `last-updated` | Present, ISO 8601 date (YYYY-MM-DD) |

Check optional fields if present:

| Field | Rule |
|---|---|
| `audience` | Only valid tags: `agent`, `supervisor-qa`, `administrator`, `platform-operator`, `partner`, `conversation-designer`, `developer-integrator` |
| `audience` | Retired tags must NOT appear: `hosting-partner`, `reseller-partner`, `platform-overview` |

### 3b. Content placement

Check that the file is in the correct section and persona subfolder:

1. What `doc-type` does the frontmatter declare?
2. Does the file path match the section for that `doc-type`?
   - `tutorial` → `Getting_Started/`
   - `explanation` → `Capabilities/` or `Solutions/` or `Platform_Overview/`
   - `how-to` → `How-to_Guides/<PersonaFolder>/`
   - `reference` → `Reference/`
   - `landing` → any `index.md`
3. If `audience` is set, is the file in the correct persona subfolder per the `Content_Placement_Guide.yaml` persona `how_to_folder` / `getting_started_folder` values?
4. Check edge cases that apply to this file's path:
   - `channel_naming_convention` — if under `Capabilities/Digital_Channels/`, must be `<Channel>/index.md`
   - `connector_docs` — connector overview goes in Capabilities, config steps go in How-to_Guides/Developer_Integrator
   - `multi_audience_content` — content must live in one folder only; other personas link to it
   - `quality_management` — capability overview in Capabilities/Quality_Management/, task guides in How-to_Guides/Supervisor_and_QA_Lead/
   - `routing_and_queues` — capability overview in Capabilities/Routing_and_Queue_Management/, config steps in How-to_Guides/Administrator/

### 3c. Diátaxis discipline

Read the content and check for type bleed:

| If doc-type is… | Must NOT contain… |
|---|---|
| `explanation` | Step-by-step numbered instructions, "Click X", "Enter Y", "Press Z" |
| `how-to` | Explanations of why a feature exists or how it works conceptually |
| `tutorial` | Deep task coverage beyond a single onboarding session |
| `reference` | Narrative prose, opinion, or task walkthroughs |
| `landing` | Primary content — must only orient and link |

### 3d. Sidebar check (only if `sidebars.js` changed)

If `sidebars.js` is among the changed files, check:

1. Top-level section order matches the fixed canonical order from `sidebar_top_level_order` in the YAML:
   `Getting Started → Solutions → Platform Overview → Capabilities → How-to Guides → Reference`
2. No section uses `{ type: 'autogenerated' }` on a directory whose `index.md` is the category link
3. No `index.md` appears both as the category `link` AND inside `items: []`

---

## Step 4 — Check open audit triggers

Read the `audit_triggers` section of `Phase3/Content_Placement_Guide.yaml`.

For any trigger with `status: open`:
- Check whether the changed files fall under the trigger's `sweep` path
- If yes, verify the trigger's `check` condition against those files
- Report whether the changed files comply or need further work

---

## Step 5 — Produce the review report

Output a structured report:

```
# Doc Review — [date]

## Files reviewed
- list each file

## Findings

### FAIL — must fix before merge
- [file path]: description of the issue and what rule it violates

### WARN — should fix
- [file path]: description of the concern

### PASS
- [file path]: summary of what was checked and confirmed

## Audit trigger status
- [trigger name] (status: open/closed): whether changed files comply

## Summary
One or two sentences: overall health of the change, what to act on first.
```

If there are no failures, say so explicitly so the author knows the change is clear to merge.
